# 高生产力反馈闭环协议（2026-08-17）

目的：把真实交付后的反馈变成下一次改进，不只靠我自己生成的示例。

## 反馈分类

| 反馈类型 | 含义 | 处理方式 |
|---|---|---|
| 决策者质疑 | 关键人觉得不成立、风险未回应 | 回到受众、目标和最危险反方问题 |
| 数据错误 | 数字、来源、政策、法律判断有误 | 先修正，再更新事实核验协议 |
| 结构缺失 | 漏了关键章节、评分项或行动项 | 更新对应场景模板 |
| 写作手法未入稿 | 内容对但表达平淡、无节奏、无钩子 | 重写段落，不只做终审 |
| 读者弃读 | 开头、章节、场景没留住人 | 按弃读点定位并修改钩子 |
| 人物无感 | 读者不关心人物 | 回查欲望、恐惧、缺陷、关系、代价 |
| 结局不接受 | 结局不符合故事逻辑或读者预期 | 区分漏洞和口味，按作者判断调整 |
| 平台/合规问题 | 违规、版权、AI 标注、审核失败 | 更新平台规范协议，发布前强制检查 |
| 真实材料不足 | 关键参数、用户、市场、数据缺失 | 标“待核验”，向用户索要真实材料 |

## 闭环流程

1. 记录：交付后收到用户、读者、评审人、平台数据时，按分类记录。
2. 归因：区分“反馈暴露了真实缺陷”和“反馈只是口味偏好”。
3. 定位：找到具体段落、模板字段、数据或判断尺，而不是只改一句话。
4. 修改：先改结构和逻辑，再改表达和文采，最后做合规检查。
5. 更新：把经验回灌到 `高生产力输出自检清单.md`、`高生产力场景模板.md`、`行业模板与评审标准库.md` 和 test-prompts。
6. 归档：用 `scripts/archive_work_product_feedback.py` 写入 `运行目录/学习记录/高生产力真实反馈归档-2026-08-17.md`。
7. 复盘：每 10 条反馈或每月做一次复盘，找出最薄弱输出类型和最高频真实缺口。

## 纪律

- 不因单条评论推翻整体作品，不因短期热度破坏故事逻辑。
- 真实反馈优先于我的自我判断，但需要区分事实性问题和偏好性问题。
- 后台数据、评审记录、编辑意见属于真实材料；没有数据时标“待接入”，不编造反馈。
