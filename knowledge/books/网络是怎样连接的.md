# 《网络是怎样连接的》技能包（14 个）

## 1. 端到端网络全貌
- R：理解网络不能只背单个协议，要从浏览器输入网址到网页显示的完整路径看系统如何协作。
- I：把“某个网络技术”换成“它在整条发送、转发、接收链路上处于哪一环”。
- A1：本书从浏览器、协议栈、网卡、交换路由、接入网、运营商、防火墙、缓存到 Web 服务器逐层追踪一个请求。
- E：分析网络问题时先画端到端路径，标出每一段负责的设备和协议，再定位故障点。
- B：一本书只能覆盖典型场景，实际网络还有移动、云、专线和多种接入方式。

## 2. URL 解析与 HTTP 请求
- R：浏览器先解析 URL 的协议、服务器、端口和路径，再按 HTTP 生成请求消息。
- I：把“输入网址就出网页”换成“请求包含对什么、做什么、头字段和消息体”。
- A1：HTTP 用 GET/POST 等方法表达操作，URI 指向资源，状态码表达结果。
- E：排查 Web 问题先看 URL 是否解析正确、方法是否符合场景、请求和响应头是否完整。
- B：现代 Web 已大量使用 HTTPS、HTTP/2、API 和代理，需按现行版本补核。

## 3. DNS 域名解析
- R：域名方便人使用，IP 地址方便路由器处理；DNS 把域名解析为 IP，并依靠层次结构和缓存提速。
- I：把“上不了网”换成“是域名解析失败、IP 可达失败，还是应用层失败”。
- A1：全世界 DNS 服务器接力查询；缓存会加速响应，也有有效期和失效问题。
- E：网络排障先确认 DNS 是否正常，再检查连接和服务器，不把症状当结论。
- B：DNS 故障不等于全部网络故障，部分应用使用 IP 直连时可能仍可工作。

## 4. TCP/IP 与套接字
- R：应用程序不直接控制网络，而是通过 Socket 库委托操作系统协议栈，用套接字记录通信状态。
- I：把“发消息”换成“创建套接字、填入控制信息、调用收发接口、关闭连接”。
- A1：套接字实体是记录通信对象、端口、状态和缓冲区的内存空间。
- E：判断应用通信问题时先看程序是否建立套接字、端口是否正确、状态处于哪个阶段。
- B：不同操作系统的协议栈实现不同，但对外协议和重要控制信息是共通的。

## 5. TCP 连接与可靠传输
- R：TCP 通过 SYN、ACK、序号、窗口和重传机制，在不可靠网络上提供可靠字节流。
- I：把“发了就应该到”换成“发送方是否确认、接收方是否已收、超时后是否重发”。
- A1：连接阶段交换初始序号；收发阶段用序号和 ACK 号检查遗漏；断开时确认后再删除套接字。
- E：分析卡顿或丢包时，先看连接是否建立、确认是否返回、重传是否频繁。
- B：TCP 可靠传输不等于网络不断或服务器可用；网络中断和宕机仍会失败。

## 6. IP 与以太网包传输
- R：IP 负责跨网选路，以太网负责同一子网内的传输；网络包由头部和数据组成。
- I：把“数据发送”换成“IP 头部定目的地，MAC 头部定下一跳，路由器和交换机各管一层”。
- A1：路由器按 IP 地址查路由表，交换机/集线器按以太网规则转发，ARP 把 IP 映射到 MAC。
- E：抓包分析时先区分 IP 层和以太网层，再看每跳的地址和转发结果。
- B：IP 选路和以太网转发只是模型，实际有无线、VLAN、隧道和 SDN 等变体。

## 7. 集线器、交换机与路由器
- R：集线器、交换机和路由器在网络中分工不同：集线器广播式转发，交换机按 MAC 表转发，路由器按路由表选路。
- I：把“网络设备都一样”换成“哪台设备负责子网内、哪台负责跨网、哪台负责接入互联网”。
- A1：家用路由器集成交换机、DHCP、NAT 和路由功能，所以看似简单但内部职责复杂。
- E：分析局域网故障先判断是设备转发、地址分配、NAT 还是路由表问题。
- B：设备功能会集成，分析时按逻辑层拆开，不因一个盒子而混淆职责。

## 8. 接入网与网络运营商
- R：从家庭或公司路由器进入互联网，需要经过接入网、运营商接入点和骨干网。
- I：把“连上路由器就等于到互联网”换成“接入线路、运营商路由和骨干网接力是否都正常”。
- A1：ADSL、FTTH、专线等接入方式不同；骨干网由大量运营商路由器互联组成。
- E：判断外网问题先区分用户侧、接入侧和骨干侧，再决定谁能处理。
- B：接入网技术和运营商拓扑会持续变化，具体性能需用实测数据验证。

## 9. 防火墙、缓存与负载均衡
- R：服务器局域网入口常有防火墙过滤危险包，缓存服务器保存可复用数据，负载均衡分散请求。
- I：把“服务器收到所有请求”换成“安全过滤、缓存命中、负载分配和源站处理是否已分离”。
- A1：防火墙像门口的保安，缓存减少源站压力，负载均衡把请求分发到多台服务器。
- E：性能和安全排查先看请求是否被防火墙拦截、缓存是否生效、负载分配是否均衡。
- B：安全配置、缓存一致性和负载策略都需要结合业务验证，不能只看单点。

## 10. Web 服务器处理请求
- R：服务器收到网络包后，由协议栈解包还原请求，Web 程序解析并生成响应，再沿原路径返回。
- I：把“服务器返回网页”换成“从网卡、协议栈、套接字、Web 程序到文件/程序的完整处理链”。
- A1：响应消息包含状态码、头字段和网页数据；CGI 等程序可动态生成内容。
- E：服务端问题先分层检查网络接收、协议解析、应用逻辑和响应生成。
- B：现代服务器还有容器、反向代理、应用框架和数据库，问题常跨越多个组件。

## 11. 分层与黑箱思想
- R：网络协议把内部实现视为黑箱，只从外部规定职责，使不同厂商和系统可以互操作。
- I：把“知道每一步细节”换成“每一层要提供什么接口、对上层保证什么、对下层依赖什么”。
- A1：TCP/IP 采用分层委派，应用层、TCP/UDP、IP、网卡驱动和硬件各有分工。
- E：复杂系统分析先定层，再按接口和保证检查，不把实现细节混进契约。
- B：黑箱思想提高兼容性，但排障时仍需进入具体实现检查状态。

## 12. TCP 与 UDP 协议选择
- R：TCP 提供可靠、有序、重传和流控，UDP 轻量、低延迟、适合短控制消息和实时传输。
- I：把“都用 TCP”换成“这个场景更重视可靠性还是延迟，丢失后能否重传”。
- A1：浏览器等一般应用用 TCP，DNS 查询等短控制数据用 UDP。
- E：设计或排查通信时先确认协议选择是否匹配可靠性和延迟需求。
- B：现代实现还有 QUIC 等新协议，选择需要结合网络环境和应用约束。

## 13. 网络排障与证据链
- R：网络问题有多个可能环节，要用端到端路径、分层检查、抓包和实测证据缩小范围。
- I：把“可能坏了”换成“哪一层、哪个设备、哪段链路、哪条证据支持这个判断”。
- A1：DNS、TCP 连接、路由、NAT、防火墙、服务器和应用都可能成为故障点。
- E：排障先记录时间、地址、包方向、错误码和复现步骤，再逐步排除假设。
- B：不抓包、不查状态、只看表象会误判；证据不足时明确标“待验证”。

## 14. 网络安全与工程边界
- R：网络传输机制本身不负责应用安全，防火墙、加密、身份认证和运维纪律共同构成防线。
- I：把“能连通就安全”换成“数据是否加密、访问是否授权、入口是否有过滤、敏感信息是否暴露”。
- A1：HTTP 默认明文，HTTPS 和加密通信在现代 Web 中承担机密性和完整性。
- E：涉及网络方案时先识别资产、入口、信任边界和失败路径，再设计保护措施。
- B：本书偏基础科普，不替代安全审计、合规评估或生产运维方案；具体环境要实测。

## 边界
- 本书为 2016 年前后的网络科普教材，部分协议版本、设备和安全实践已更新。
- AI 可用于理解网络模型、分析故障逻辑和辅助排障，不替代真实设备操作、安全审计或生产变更。
- 涉及生产网络、敏感数据和合规要求时，应由具备资质的网络和安全专业人员处理。
